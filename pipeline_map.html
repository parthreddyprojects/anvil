00 Problem Statement + Landscape Scan + MECE Decomposition Human Checkpoint
The most critical step. Anvil acts as an engagement manager — challenges one-sided framing ("protect" → "optimize"), tests for scope, ensures the question has a quantified decision sensitivity break point. Then scans live news in two tiers (snippets first, then full articles on gaps), and decomposes into MECE buckets with investigative sub-questions.
INPUTS
User: Topic
Raw problem statement, 1-2 sentences. e.g., "What should India's PSU refiners do about the Hormuz closure?"
User: Audience
Who acts on this? e.g., "CMD, Director Refining, Director Finance; MoPNG has pricing veto"
vault/issue_tree_vault.json
5 decomposition methods (algebraic, process, causal, segmentation, situation) + 8 fully worked MECE examples
→
WHAT HAPPENS
1. Problem Worksheet SONNET
Completes 6-component framework: basic question, context, criteria for success, scope (in/out), constraints, stakeholders (decision-makers, supporters, blockers), decision sensitivity break point, key assumptions.
2. Landscape Scan — Tier 1 (Fast) HAIKU
Generates 12 search queries → DuckDuckGo search (3 news + 3 web results per query) → Haiku summarizes all snippets into a landscape overview. Purpose: cheap, fast scan of what's happening right now.
3. Landscape Scan — Tier 2 (Deep) SONNET
Reads Tier 1 summary, identifies gaps and angles worth going deeper on → generates 5-6 depth queries → fetches full article text from URLs (6 parallel workers, skip paywalls) → Sonnet combines Tier 1 + Tier 2 into a 2-3 page current events summary.
4. Core MECE Buckets SONNET
Picks decomposition method based on problem type. Generates 4-6 mutually exclusive, collectively exhaustive buckets — each framed as an open question ("How exposed is Jamnagar's crude supply?"), not a topic label. Uses vault examples for calibration.
5. Auxiliary Forces Check SONNET
Reviews the landscape scan for external dimensions NOT covered by core buckets (regulatory, geopolitical, competitive, second-order). Adds 1-3 auxiliary buckets if gaps exist. Only additions, never removals.
6. Sub-questions HAIKU ×N PARALLEL
For each bucket: generates 5-8 specific investigative questions. All questions are factual ("What is the current unhedged exposure?") not prescriptive ("How should they hedge?"). Runs in parallel across buckets (ThreadPoolExecutor, 6 workers).
CHECKPOINT: Confirm PS + MECE
Human reviews the problem statement and decomposition. Can challenge framing, add/remove buckets, edit questions. Must explicitly confirm before pipeline proceeds.
→
OUTPUT FILES
mece/0_problem_worksheet.json
Full 6-component problem worksheet. Includes decision sensitivity break point — the specific condition under which the opposite answer becomes correct.
mece/decomposition.json
SMART problem statement + sections array (each: section_id, title, rationale, questions array). This is the master file — every downstream step reads from it.
landscape_scan/landscape.json
Full Tier 1 + Tier 2 scan data: all articles (title, URL, text), snippets, events, search queries used. Typically ~150KB. Timestamped — this is the "we have current data" evidence.
landscape_scan/landscape_summary.md
2-3 page readable summary of current events relevant to the problem. Fed into research debrief later to prove the LLM had live data.

1.5 80/20 Tiering Auto
Scores every sub-question against the decision sensitivity break point. Tier 1 questions would flip the recommendation if answered differently — these get the most research depth. Tier 3 can be extrapolated. This is how the pipeline allocates attention.
INPUTS
mece/decomposition.json
All sections + sub-questions
Decision sensitivity break point
From problem worksheet — the condition that flips the answer
→
WHAT HAPPENS
Tier Scoring HAIKU
For each sub-question: would this answer flip the recommendation?
Tier 1: Yes — triangulate from 3+ sources, deep research.
Tier 2: Important context but won't flip alone — 1-2 sources.
Tier 3: Can be extrapolated from Tier 1/2 answers — minimal research.
→
OUTPUT FILES
tiers/tiers.json
Array of {question_id, tier (1/2/3), reason}. Summary counts. Tier labels get merged back into the decomposition sections in memory.
02 Deep Research Human Checkpoint
The research engine. For each MECE bucket: generate targeted search queries, search the web, fetch full articles, and synthesize findings into a research brief that answers every sub-question with sources. Human can inject proprietary data at this point. This is the longest step (~15 min).
INPUTS
mece/decomposition.json
Tiered sections + sub-questions. Tier 1 questions get deeper research.
landscape_scan/landscape.json
Current events context from Step 0 — avoids re-searching what's already known.
inputs/research/ (optional)
Human-provided files: PDFs, CSVs, docs. Injected as HIGH confidence evidence. e.g., internal inventory data, contract terms, proprietary forecasts.
→
WHAT HAPPENS
1. Client Context Inference HAIKU
Reads problem + audience → infers what internal data systems they likely have access to (e.g., "Reliance trading desk has real-time VLCC freight data"). Used to flag PROPRIETARY items in research requirements.
2. Research Requirements ×N HAIKU ×N PARALLEL
Per bucket: what data is needed, what sources exist, is it PUBLIC or PROPRIETARY, is it MUST-HAVE or NICE-TO-HAVE. Generates research checklist.
CHECKPOINT: Research Input Choice
A: Proceed with public data only (proprietary items marked LOW confidence)
B: Upload files to inputs/research/
C: Quit & gather data manually, resume later
D: Selective — provide data for some items, skip others
3. Search Queries ×N HAIKU ×N
Per bucket: 10 targeted search queries. Targets: government data portals, company investor relations, think tanks, industry trackers, Wikipedia, academic papers. Avoids generic queries.
4. DuckDuckGo Web Search
Sequential per bucket (1.5s throttle). Per query: 3 news results + 3 web results. Skips paywalled sources (Reuters, FT, WSJ, Bloomberg, NYT, Economist, Barron's, SeekingAlpha). Collects snippet text + URLs.
5. Full Article Fetch (6 parallel workers)
Per bucket: up to 10 URLs, prefers non-paywalled. Fetches full HTML, strips scripts/styles/nav, extracts clean text. Returns up to 5 full articles per bucket.
6. Bucket Research Brief ×N SONNET ×N PARALLEL
Per bucket: receives topic, bucket title, all sub-questions, 30+ search snippets, 5+ full articles, current events context, human-provided data. Answers each question with BOTTOM LINE (1-2 sentences) + supporting detail. Sources every fact. Marks model reasoning as [LLM reasoning]. Saves as bucket_NN.md.
→
OUTPUT FILES
research/research_brief.json
Client context + per-bucket requirements: data needed, source type (PUBLIC/PROPRIETARY/EXPERT), priority (MUST-HAVE/NICE-TO-HAVE), suggested sources.
research/research_checklist.md
Human-readable checklist: MUST-HAVE items flagged, PROPRIETARY items highlighted with specific "client ask" text.
research/bucket_01.md … bucket_N.md
Per-bucket research findings. Each sub-question answered with sourced data. This is the raw evidence layer.
research/compiled.md
All bucket files joined with --- separators. This is what feeds into the working document and debrief. If empty on resume, pipeline rebuilds from individual bucket files.
03 Working Document + Research Debrief Human Checkpoint
Research gets compiled into a structured working document (bottom-line-up-front per question) and a 2-5 page research debrief written like you're walking into the partner's office. Every fact anchored to time period, source, and comparison baseline. Runs in parallel with Step 2 when possible.
INPUTS
research/bucket_*.md
Per-bucket research findings from Step 2
mece/decomposition.json
Sub-questions to structure the working document around
landscape_scan/landscape_summary.md
Fed into debrief prompt so the LLM knows it has live web research and doesn't disclaim
→
WHAT HAPPENS
1. Working Doc Per Bucket SONNET ×N PARALLEL
Per bucket: takes research findings + questions → writes executive-level narrative. BOTTOM LINE first, then supporting detail. Where data unavailable, states what's known + uncertainty naturally (no "DATA GAP" labels). Preserves source citations and [LLM reasoning] tags.
2. Research Debrief SONNET
2-5 page partner debrief. Structure: (1) Bottom line up front — single most important thing with specific numbers. (2) What we found — per research area with anchored data points. (3) What remains uncertain — where estimates replace confirmed data. (4) Early signals — cross-cutting observations and tensions. Explicitly told: "This was built from LIVE WEB RESEARCH — do not disclaim lack of data."
CHECKPOINT: Review Debrief
Human reviews findings. Can add insights ("we know the actual inventory is X"), give feedback ("bucket 3 is wrong about Y"), or approve to proceed.
→
OUTPUT FILES
working_doc/working_document.md
Full compiled working document: all buckets, all questions answered. This is the foundation for synthesis.
research/debrief.md
Partner-ready research debrief in markdown.
research/debrief.html
Styled HTML version → embedded in "Research Debrief" tab of output.html
04 Synthesis — Findings → Patterns → Inferences Human Checkpoint
Where the engine earns its keep. Three passes: extract key findings per bucket, then read ACROSS all buckets to find patterns (what converges, what contradicts, what surprises), then derive "so what" inferences that no single bucket could surface alone. This is exactly what a chat window can't do — the context isn't big enough to hold the full picture.
INPUTS
working_doc/bucket_*.md
Per-bucket working document sections
mece/decomposition.json
Tier 1 questions — synthesis focuses on decision-critical findings
→
WHAT HAPPENS
1. Extract Findings ×N SONNET ×N PARALLEL
Per bucket: extract 3-5 KEY FACTS. Each must have a specific number, time period, comparison baseline, and source. Written like a CEO summary — simple words, no jargon. Preserves "(per source, date)" and "[LLM reasoning]" tags. Each finding gets an ID (F1.1, F2.3) and confidence (HIGH/MEDIUM/LOW).
2. Cross-Bucket Patterns SONNET
Reads ALL findings across ALL buckets. Identifies 5-8 patterns:
CONVERGENCE: Multiple independent findings point same direction
TENSION: Contradictory findings create a dilemma
SURPRISE: Breaks expected pattern
BINDING CONSTRAINT: One finding limits everything else
CASCADE: Finding A triggers consequence B
Each pattern cites specific finding IDs (F1.1, F3.2) and rates importance (CRITICAL/IMPORTANT/NOTABLE).
3. "So What" Inferences SONNET
For each pattern: what does it IMPLY for the decision-maker? Connects back to the problem statement. Points toward (but doesn't state) possible hypotheses. Includes the key number/threshold. Each inference gets an ID (I1, I2) and cites its source pattern (P1, P2).
CHECKPOINT: Review Synthesis
Can add insights ("the PSU pricing constraint and the margin opportunity are connected — that's the real insight"), challenge patterns, or approve.
→
OUTPUT FILES
synthesis/1_findings.json
Per-bucket findings: F1.1, F2.3… Each with finding text, confidence, source question, tier.
synthesis/2_patterns.json
Cross-bucket patterns: P1, P2… Each with type, name, statement, supporting finding IDs, importance.
synthesis/3_inferences.json
Inferences: I1, I2… Each with so_what, key_number, implies_for_decision, source pattern ID.
synthesis/synthesis.json + .html
Combined file (findings + patterns + inferences). HTML version → "Synthesis" tab.
05 Hypotheses — Generate, Stress-Test, Kill Human Checkpoint
The step most AI tools skip entirely. Converts synthesis inferences into 5-8 testable hypotheses that directly answer the problem statement. Then actively tries to kill them with a structured 6-point stress test. Survivors become the final brief's backbone. The dead go to the graveyard — with full reasoning. ACH diagnosticity scoring identifies which findings actually distinguish between competing hypotheses.
INPUTS
synthesis/synthesis.json
Findings (F), Patterns (P), Inferences (I) — the full evidence chain
Decision sensitivity break point
The quantified condition from Step 0 that flips the answer
inputs/hypothesis/ (optional)
Evidence files to confirm or disprove specific hypotheses. e.g., actual inventory data, confirmed contract terms.
→
WHAT HAPPENS
1. Generate Hypotheses SONNET
Converts inferences into 5-8 hypotheses that DIRECTLY ANSWER the problem statement. Pyramid principle: inference (pattern implies X) → hypothesis (therefore do Y because X). BINDING CONSTRAINT patterns first. TENSION patterns generate competing hypotheses. Each hypothesis cites P/F/I IDs, includes specific number/threshold, states its own break point.
2. Six-Point Stress Test SONNET
Per hypothesis, 6 failure modes tested:
(1) Evidence-claim mismatch — does the evidence actually support this? → KILL if no
(2) Break point plausibility — is the break point realistic?
(3) Internal consistency — contradicts another active hypothesis? → KILL if yes
(4) Confidence calibration — is confidence rating justified by evidence quality?
(5) Steel-man counterargument — strongest possible objection
(6) Diagnosticity — does this hypothesis make different predictions than alternatives?
Status after: confirmed, uncertain, or killed.
3. Coverage Check HAIKU
Is every MECE bucket represented by at least one active hypothesis? If not, flags the gap and explains why — either the bucket's findings didn't support any testable claim, or a hypothesis was killed that covered it.
4. ACH Diagnosticity Matrix SONNET
Analysis of Competing Hypotheses: for each key finding, score it against ALL active hypotheses as C (consistent), I (inconsistent), or N (neutral). A finding that's C with many hypotheses has LOW diagnosticity (doesn't help you decide). A finding that's C with one but I with others has HIGH diagnosticity (it distinguishes). Adjusts confidence ratings based on diagnosticity.
CHECKPOINT: Proof Input
A: Proceed — some hypotheses may remain UNCERTAIN
B: Upload evidence files
C: Quit & gather evidence, resume later
D: Selective — provide evidence for specific hypotheses
→
OUTPUT FILES
hypotheses/hypotheses.json
Full hypothesis tree: governing_hypothesis (strongest single answer), hypotheses array (H1-HN: statement, evidence_for, evidence_against, break_point, confidence, status, stress_checks), graveyard (killed hypotheses with kill reason), coverage map.
hypotheses/diagnosticity.json
ACH matrix: per-finding scores against all hypotheses, high-diagnosticity findings, low-diagnosticity warnings, confidence adjustments.
hypotheses/proof_checklist.md
What specific evidence would confirm or disprove each active hypothesis. Named providers and deadlines for internal data.
06 Final Document Human Checkpoint
Generates a 3-5 page executive strategic brief in HTML. Two LLM passes: first generates the prose, then a separate critique pass rewrites for voice, structure, and punch. The document you'd put in front of a senior partner.
INPUTS
hypotheses/hypotheses.json
Governing hypothesis + active hypotheses + graveyard
synthesis/synthesis.json
Findings, patterns, inferences for evidence context
Problem statement + audience
From state.json — grounds the document in the original question
→
WHAT HAPPENS
1. Generate Prose SONNET
3-5 page HTML document. Fixed structure:
h1: Thematic title (3-8 words, e.g., "Jamnagar's Thirty-Day Clock")
p.ps: Original problem statement in italic
h2: Governing hypothesis (one sentence conclusion)
h2 Context: 2-3 paragraphs, sets the scene with one anchor number
h2 What We Believe: Numbered strategic beliefs (1 sentence each)
h2 per hypothesis: Headline IS the conclusion. Bold claim → evidence → break point → confidence
h2 Decisions Required: Numbered list: owner, deadline, cost, dependencies, consequence of inaction
h2 Tested and Rejected: Killed hypotheses with one-sentence kill reason
h2 Data Gaps: What needs verification, who provides it, by when
2. Critique + Rewrite SONNET
Separate pass rewrites the entire document:
• Every paragraph starts with bold lead-in (3-8 words)
• One idea per sentence. Short. Direct.
• Delete sentences with no new fact or insight
• Kill all meta-commentary ("confidence: HIGH", "Tier 1", "break point")
• Preserve all "(per source, date)" citations and "[LLM reasoning]" tags
• Unsourced numbers get "(unverified)"
• End each section with punch, not hedge
→
OUTPUT FILES
final_document_draft.html
First LLM pass — before critique rewrite
final_document.html
Polished executive brief → embedded in "Report" tab of output.html. This is the primary deliverable.
07 Appendix — Proof Charts Auto
Every claim in the final document with a hard number maps to exactly one proof slide. Chart type chosen by data relationship (ranking → bar, change over time → line, part-to-whole → pie, correlation → scatter, etc.). 4-6 slides rendered with Apache ECharts. Must use 3+ different chart types. Never invents values — if no sourced number, no chart.
INPUTS
final_document.html
Parsed to plain text. LLM extracts claims that contain hard numbers worthy of a proof slide.
vault/chart_vault.json
Chart design decision tree: data relationship → chart form. 5 relationship types (component, item, time series, distribution, correlation), each with chart form, rules, anti-patterns. Design principles: strategic attention, declutter, direct the eye, color semantics. ECharts styling defaults.
→
WHAT HAPPENS
1. Map Claims to Slides SONNET
4-6 slides. Per slide: exact claim sentence from document, chart type (10 options: bar, horizontal_bar, line, area, waterfall, pie, donut, scatter, gauge, funnel, sankey, heatmap), chart_data (labels, values, colors), action_title (conclusion headline), subtitle (units, period, source), source_line. Must use 3+ different chart types. Colors: red (#ef4444) = bad, green (#22c55e) = good, blue (#2563eb) = neutral. Labels max 25 chars.
2. ECharts HTML Renderer
Builds self-contained HTML with Apache ECharts CDN. Each slide: header (Appendix N), title, subtitle, chart div (echarts.init + setOption), conclusion, source. Keyboard navigation (arrow keys), scroll detection, progress bar.
→
OUTPUT FILES
appendix/slides.json
Slide specs: appendix_num, claim_sentence, chart_type, chart_data, action_title, subtitle, conclusion, source_line.
appendix.html
Interactive proof slides → embedded in "Appendix" tab of output.html
